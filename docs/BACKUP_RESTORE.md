# 🛡️ دليل النسخ الاحتياطي والاستعادة (L-15)

> [!IMPORTANT]
> **القاعدة الذهبية:** "نسخة احتياطية لم يتم اختبار استعادتها هي مجرد فرضية، وليست نسخة فعلية."
> وُجدت هذه الوثيقة لتحويل الفرضية إلى خطة عمل موثوقة.

تعتمد المنصة على قاعدة بيانات SQLite واحدة تحمل **كل شيء**: الحسابات، الاشتراكات، المدفوعات، البوتات، توكنات الربط، والمحادثات.
بالإضافة إلى مجلد `uploads/` الذي يحوي صور إيصالات الدفع (الدليل المالي الوحيد في حالات النزاع).
**فقدان أي منهما لا يعتبر عطلاً تقنياً، بل تهديداً مباشراً لاستمرارية المشروع.**

---

## 1. 🔄 النسخ الاحتياطي اليومي (الآلي)

تم إعداد النظام ليقوم بنسخ احتياطي آلي يومياً في تمام الساعة 3 فجراً عبر `cron`:

```bash
0 3 * * * /opt/botyalla/deploy/backup.sh >> /var/log/botyalla-backup.log 2>&1
```

**ما الذي يتم نسخه إلى مسار `/var/backups/botyalla`؟**

| المورد المنسوخ | أداة النسخ | الأهمية والسبب |
|---|---|---|
| **قاعدة البيانات** (`botyalla.db`) | `sqlite3 .backup` | تُنسخ بأمان. **(ممنوع استخدام `cp` أبداً)** لتجنب التقاط القاعدة في منتصف معاملة ما ينتج عنه ملف تالف، خاصة مع استخدام وضع WAL. |
| **مجلد المرفقات** (`uploads/`) | أرشيف مضغوط | يحتوي على إيصالات الدفع وهو المرجع القانوني لأي نزاع مالي. |
| **ملف البيئة** (`.env`) | نسخ مباشر | يحتوي على `FLASK_SECRET`؛ بدونه ستُبطل جميع جلسات المستخدمين عند الاستعادة. |

### ✨ مميزات السكربت `backup.sh`:
1. **الفحص الفوري:** يقوم السكربت بفحص سلامة النسخة فور أخذها باستخدام `PRAGMA integrity_check` ويحصي عدد المستخدمين. أي نسخة غير مكتملة أو تالفة تُحذف فوراً ويخرج السكربت بخطأ.
2. **الأمان أولاً:** لا يتم حذف النسخ القديمة إلا بعد **نجاح** عملية النسخ الجديدة. لضمان عدم بقاء الخادم بلا نسخ احتياطية في حال فشل العملية.
3. **تنبيهات فورية:** يرسل لك إشعاراً فورياً على تليجرام عند أي فشل (في حال تم ضبط `ALERT_BOT_TOKEN` و `ALERT_CHAT_ID`).

> [!WARNING]
> ### 🔴 الفجوة الحرجة: النسخة على نفس القرص
> عطل القرص الصلب سيقضي على النظام ونسخه الاحتياطية معاً. **يجب عليك ضبط `RCLONE_REMOTE`** لرفع النسخ خارج الخادم:
> ```bash
> curl https://rclone.org/install.sh | sudo bash
> rclone config                      # قم بتسمية الوجهة gdrive
> # أضف التالي في /etc/environment أو داخل وحدة systemd:
> RCLONE_REMOTE="gdrive:botyalla_backups"
> ```

## 2. 👁️ التحقق الأسبوعي (دقيقتان فقط)

إجراء سريع للتأكد من أن الأمور تسير كما هو مخطط لها:

```bash
# هل نسخة الأمس موجودة وحجمها منطقي؟
ls -lh /var/backups/botyalla | tail -5

# هل سجلت العملية عبارة "db ok"؟
tail -20 /var/log/botyalla-backup.log
```

> [!CAUTION]
> **علامات الخطر:** انخفاض مفاجئ في حجم الملفات • توقف النسخ ليومين متتاليين • ظهور فشل في `integrity_check` داخل السجل • حجم النسخة بضعة كيلوبايتات فقط.

## 3. 🧪 البروفة الشهرية (محك الحقيقة)

لا تختبر أدوات الاستعادة لأول مرة يوم وقوع الكارثة. خصص 30 دقيقة شهرياً لتنفيذ استعادة تجريبية على **خادم اختبار**:

```bash
# 1) اختبار وهمي (Dry Run) — آمن تماماً، يمكن تشغيله على خادم الإنتاج:
DRY_RUN=1 deploy/restore.sh /var/backups/botyalla/db_2026-09-11_0300.sqlite.gz

# 2) استعادة كاملة وحقيقية — على خادم الاختبار:
sudo APP_DIR=/opt/botyalla deploy/restore.sh \
     /var/backups/botyalla/db_2026-09-11_0300.sqlite.gz \
     /var/backups/botyalla/uploads_2026-09-11_0300.tar.gz
```

> [!TIP]
> **التوثيق هو RTO الحقيقي:** بعد كل بروفة استعادة، دوّن في `PROJECT_MEMORY.md` ما يلي: التاريخ، عمر النسخة، الزمن المستغرق من بدء الاستعادة حتى عودة الخدمة، وما هي العوائق التي واجهتك. هذا الزمن هو الإجابة الدقيقة عند سؤال العملاء "متى ستعود الخدمة؟".

### ⚙️ آلية عمل `restore.sh` بالترتيب:
1. يفك الضغط ويفحص الملفات **قبل لمس قاعدة البيانات الحالية**. النسخ التالفة تُرفض لتبقى الخدمة قيد التشغيل.
2. يُحصي عدد المستخدمين، البوتات، والمدفوعات ويعرضها للمقارنة بالوضع الحالي. (إذا كانت النسخة أقدم من الحالية، سيطلب منك تأكيداً كتابياً `YES`).
3. يوقف الخدمة مؤقتاً لتجنب تلف القاعدة أثناء استبدالها.
4. **يُزيح القاعدة الحالية** ولا يحذفها (يسميها `botyalla.db.before-restore.TIMESTAMP`)، وينظف ملفات الذاكرة المؤقتة (WAL/SHM).
5. ينقل القاعدة الجديدة ويستعيد المرفقات، يعيد ضبط الصلاحيات، ثم يُشغّل الخدمة ويتحقق من استجابتها.

## 4. 🚨 عند الكارثة الحقيقية

> [!CAUTION]
> **لا تبدأ بالاستعادة فوراً!** ابدأ بالتشخيص أولاً. استعادة نسخة قديمة فوق مشكلة لم تفهمها قد يؤدي إلى خسارة بيانات اليوم دون داعٍ.

**أوامر التشخيص:**
```bash
systemctl status botyalla            # هل الخدمة متوقفة أصلاً؟
journalctl -u botyalla -n 100        # ما هو الخطأ الحقيقي المُسجل؟
df -h                                # هل القرص ممتلئ؟ (سبب شائع يبدو كتلف في القاعدة)
python3 -c "import sqlite3;print(sqlite3.connect('/opt/botyalla/botyalla.db').execute('PRAGMA integrity_check').fetchone())"
```

### 📋 مصفوفة اتخاذ القرار:
| ما تراه (التشخيص) | الإجراء المطلوب |
|---|---|
| **القرص ممتلئ** | فرّغ مساحة ثم أعد تشغيل الخدمة — **(لا تقم بالاستعادة)**. |
| **`integrity_check` سليم، لكن الخدمة لا تعمل** | المشكلة في الكود أو الإعدادات (راجع السجل) — **(لا تقم بالاستعادة)**. |
| **القاعدة تالفة فعلياً** | استعد أحدث نسخة متوفرة. |
| **حذف خاطئ ببيانات ناقصة (القاعدة سليمة)** | استعد النسخة التي تسبق تاريخ الحذف مباشرة. |

> [!NOTE]
> **بعد الاستعادة، تحقق بنفسك:**
> سجّل الدخول • تأكد من ظهور بوتاتك • جرّب تشغيل بوت • راجع آخر دفعة في لوحة الأدمن • تأكد أن مفتاح `FLASK_SECRET` لم يتغير (لو تغير ستفقد جميع جلسات المستخدمين النشطة).

## 5. 📉 ما لا تحميه هذه الخطة

لتكون على دراية تامة بمخاطر السيناريوهات التالية:

| الخطر المتوقع | موقف الخطة الحالية |
|---|---|
| **فقد بيانات آخر ≤ 24 ساعة** | ⚠️ **مقبول ضمناً.** النسخ يومي، وحدوث كارثة الساعة 2 ظهراً يعني فقدان بيانات نصف يوم. (النسخ اللحظي يتطلب تعقيداً إضافياً كـ WAL Streaming). |
| **عطل القرص الصلب بالكامل** | ❌ **غير محمي** حتى تقوم بإعداد وتفعيل `RCLONE_REMOTE`. |
| **ضياع ملف `.env`** | ⚠️ يتم نسخه دورياً، لكن **يُرجى الاحتفاظ بنسخة خارجية منه يدوياً** (فهو مفتاح كل التشفير والجلسات). |
| **ضياع توكنات البوتات** | ✅ محمية تماماً لأنها تُخزن داخل قاعدة البيانات وتعود بعودتها. |
| **اختراق الخادم وحذف النسخ** | ❌ النسخ المحلية تُحذف مع الخادم، الحل الوحيد هو النسخ الخارجي (RCLONE). |
