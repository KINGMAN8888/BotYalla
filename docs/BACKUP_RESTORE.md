# النسخ الاحتياطي والاستعادة — L-15

> **القاعدة الوحيدة في هذا الملف:** نسخة احتياطية لم تُستعَد مرّةً واحدة ليست
> نسخة احتياطية — هي فرضية. وهذه الوثيقة موجودة لتحويل الفرضية إلى خطّة.

قاعدة SQLite واحدة تحمل **كل شيء**: الحسابات، الاشتراكات، المدفوعات، البوتات
وتوكناتها، المحادثات. ومجلد `uploads/` يحمل إيصالات الدفع — وهي دليلك الوحيد
في أي نزاع مالي. فقدان أيٍّ منهما ليس عطلاً تقنياً بل نهاية للمشروع.

---

## 1) ما يجري يومياً (مضبوط سلفاً)

`deploy/backup.sh` يعمل من cron الساعة 3 فجراً:

```
0 3 * * * /opt/botyalla/deploy/backup.sh >> /var/log/botyalla-backup.log 2>&1
```

ويأخذ ثلاثة أشياء إلى `/var/backups/botyalla`:

| ما يُنسَخ | لماذا |
|---|---|
| `botyalla.db` بـ`sqlite3 .backup` | **ليس `cp`**: النسخ أثناء الكتابة يلتقط القاعدة في منتصف معاملة فيعطي ملفاً تالفاً، خصوصاً مع WAL |
| `uploads/` مضغوطاً | إيصالات الدفع — دليلك في أي نزاع |
| `.env` | يحوي `FLASK_SECRET`؛ بدونه تُبطَل كل الجلسات عند الاستعادة |

**وما يفعله أكثر من مجرّد النسخ:**

1. **يفحص النسخة فور أخذها** بـ`PRAGMA integrity_check` + عدّ المستخدمين. نسخة تالفة تُحذف ولا تُضغط، ويخرج السكربت بخطأ.
2. **لا يحذف نسخ الأمس إلا بعد نجاح نسخة اليوم.** الترتيب مقصود: فشلٌ مبكر يترك القديم مكانه بدل أن يترك الخادم بلا أي نسخة.
3. **ينبّهك على تليجرام عند أي فشل** — إن ضبطت `ALERT_BOT_TOKEN` و`ALERT_CHAT_ID`.

> ### 🔴 الفجوة الوحيدة الباقية: النسخة على نفس القرص
> عطل القرص يأخذ النسخ معه. **اضبط `RCLONE_REMOTE`** وإلا فكل ما سبق يحميك
> من الخطأ البشري وحده، لا من عطل العتاد:
> ```bash
> curl https://rclone.org/install.sh | sudo bash
> rclone config                      # سمّ الوجهة gdrive
> # في /etc/environment أو وحدة systemd:
> RCLONE_REMOTE="gdrive:botyalla_backups"
> ```

## 2) التحقّق الأسبوعي — دقيقتان

```bash
ls -lh /var/backups/botyalla | tail -5        # هل نسخة الأمس موجودة وحجمها معقول؟
tail -20 /var/log/botyalla-backup.log         # هل قال "db ok"؟
```

**علامات الخطر:** حجم ينخفض فجأة · لا نسخة منذ يومين · `integrity_check` في السجل · نسخة بحجم بضعة كيلوبايت.

## 3) البروفة الشهرية — **هذا هو البند الفعلي**

لا تجرّبها لأول مرّة يوم الكارثة. خصّص 30 دقيقة شهرياً على **خادم اختبار**:

```bash
# 1) افحص بلا أي تغيير — آمن تماماً، شغّله على الإنتاج متى شئت
DRY_RUN=1 deploy/restore.sh /var/backups/botyalla/db_2026-09-11_0300.sqlite.gz

# 2) على خادم الاختبار: استعادة كاملة
sudo APP_DIR=/opt/botyalla deploy/restore.sh \
     /var/backups/botyalla/db_2026-09-11_0300.sqlite.gz \
     /var/backups/botyalla/uploads_2026-09-11_0300.tar.gz
```

**سجّل بعد كل بروفة** (في `PROJECT_MEMORY.md`): التاريخ · عمر النسخة · الزمن من بدء الاستعادة إلى عمل الخدمة · ما تعطّل. **الزمن هو RTO الحقيقي** — وهو ما تقوله لعميل يسأل «متى ترجعون؟»، لا رقم تخمّنه.

### ماذا يفعل `restore.sh` بالترتيب

1. يفكّ الضغط ويفحص — **قبل أن يلمس أي شيء**. نسخة تالفة تُرفض وتبقى الخدمة عاملة.
2. يعدّ المستخدمين والبوتات والدفعات ويعرضها لك، ويقارنها بالحالية. لو كانت النسخة **أقدم** طلب منك كتابة `YES` صراحةً.
3. يوقف الخدمة — الاستعادة فوق قاعدة مفتوحة تعطي ملفاً تالفاً.
4. **يُزيح** القاعدة الحالية جانباً (`botyalla.db.before-restore.TIMESTAMP`) ولا يحذفها، ويزيل ملفات WAL/SHM القديمة.
5. يضع النسخة، ويستعيد الإيصالات إن مُرّرت، ويضبط الملكية، ويشغّل الخدمة ويتأكد أنها عملت.

## 4) عند الكارثة الحقيقية

**لا تبدأ بالاستعادة. ابدأ بالتشخيص** — استعادةٌ فوق مشكلةٍ لم تفهمها تفقدك بيانات اليوم بلا داعٍ.

```bash
systemctl status botyalla            # هل الخدمة أصلاً متوقفة؟
journalctl -u botyalla -n 100        # ما الخطأ الحقيقي؟
df -h                                # القرص ممتلئ؟ (سبب شائع يبدو كتلف قاعدة)
python3 -c "import sqlite3;print(sqlite3.connect('/opt/botyalla/botyalla.db').execute('PRAGMA integrity_check').fetchone())"
```

| ما تراه | افعل |
|---|---|
| القرص ممتلئ | فرّغ مساحة وأعد التشغيل — **لا تستعد** |
| `integrity_check` يقول ok والخدمة لا تبدأ | مشكلة كود أو إعداد، لا بيانات — راجع السجل |
| القاعدة تالفة فعلاً | استعد أحدث نسخة |
| حذف خاطئ (بيانات ناقصة والقاعدة سليمة) | استعد النسخة السابقة للحذف |

**بعد أي استعادة، تحقّق بنفسك:** سجّل الدخول · بوتاتك ظاهرة · شغّل واحداً · راجع آخر دفعة في لوحة الأدمن · تأكد أن `FLASK_SECRET` لم يتغيّر (لو تغيّر خرج كل المستخدمين).

## 5) ما لا تحميه هذه الخطّة — بصراحة

| الخطر | الحال |
|---|---|
| فقد بيانات آخر ≤24 ساعة | ⚠️ **مقبول ضمناً**. النسخ يومي، فكارثة الساعة 2 ظهراً تفقد نصف يوم. لحظية أقل تحتاج WAL streaming — مبالغة في هذه المرحلة، **لكن اعرف أنك تقبلها** |
| عطل القرص | ❌ **غير محمي حتى تضبط `RCLONE_REMOTE`** |
| ضياع `.env` | ⚠️ منسوخ، لكن **احتفظ بنسخة منه خارج الخادم يدوياً** — هو مفتاح كل شيء |
| توكنات البوتات | ✅ داخل القاعدة، تعود بعودتها |
| اختراق يحذف النسخ | ❌ نسخة على نفس الخادم تُحذف مع الخادم. الوجهة الخارجية هي الجواب |
