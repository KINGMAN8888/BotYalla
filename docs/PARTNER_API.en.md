# Integrating with BotYalla — Technical Partner Guide

> 🇪🇬 **النسخة العربية:** [PARTNER_API.md](PARTNER_API.md)

> For companies that want to send and receive WhatsApp messages **from their own number**,
> without dealing with Meta directly.
>
> **BotYalla is a Meta-approved Tech Provider.** Onboarding happens inside our platform —
> you never open Meta for Developers, never create an App, never build a System User, and
> never wait on an app review.

## What you get

| | |
|---|---|
| `WHATSAPP_WABA_ID` | Your WhatsApp Business Account ID — **registered in your name** |
| `WHATSAPP_PHONE_NUMBER_ID` | Your number's ID |
| **A BotYalla API key** | Replaces `WHATSAPP_ACCESS_TOKEN`. We can revoke it on its own if it ever leaks |
| **A webhook URL you register** | We forward every inbound message to your server |

The number and the business account belong to **you**. Message costs are billed to **your own
payment method inside Meta** — Meta's rate, with nothing added by us.

## Step 1 — Connect your number (3 minutes, once)

Create a BotYalla account → click **"Connect WhatsApp"** → a Meta window opens → pick or
create your WhatsApp Business Account and your number → done.

You will not touch `developers.facebook.com`, an App, a System User, or an app review.

> **Already running that number on the WhatsApp Business app?** Choose **Coexistence mode**.
> The number keeps working on your phone exactly as it does today, and the API works on it
> at the same time.

---

## Step 2 — Create your API key

**Bot → API & developers → New key.**

The key is shown **exactly once**. We store only an HMAC fingerprint of it, never the key
itself — nobody at BotYalla can read it back. Lost it? Create a new one and revoke the old.

You can **scope a key to a single bot**, so a key living on one server cannot send from
every number you own.

## Step 3 — Sending

The request shape is **identical to the WhatsApp Cloud API**. Change the base URL and leave
your code exactly as it is:

```
https://graph.facebook.com/v21.0/{PHONE_NUMBER_ID}/messages   ←  before
https://botyalla.com/api/v1/{PHONE_NUMBER_ID}/messages        ←  after
```

```bash
curl -X POST 'https://botyalla.com/api/v1/{PHONE_NUMBER_ID}/messages' \
  -H 'Authorization: Bearer by_live_xxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{"messaging_product":"whatsapp","to":"2010xxxxxxx",
       "type":"text","text":{"body":"Hello 👋"}}'
```

The response comes back **exactly as Meta returns it** — the same `messages[].id`, the same
error envelope. Templates, media and interactive messages all pass through untouched, with
no mapping on our side.

| Status | Meaning |
|---|---|
| `401` with `"type":"auth"` in the body | Your BotYalla key is wrong or revoked |
| `403` | This key is not allowed to send from this number |
| `429` | You exceeded 600 requests per minute |
| anything else | **Meta's own response**, passed straight through |

Only the first three are generated by us — everything else is Meta talking to you directly.

## Step 4 — Receiving

**Read this part carefully — it is the one thing that surprises people.**

Meta's webhook is delivered to **BotYalla's application**, because we are the app subscribed
to your WhatsApp Business Account. Your server therefore receives **nothing from Meta
directly**, and you cannot subscribe your own app using the credentials we issue — they
belong to our Meta app, not yours.

So we forward the traffic to you.

**Bot → API & developers → Receiving (webhook)** → enter your server's URL. It must be
`https` and publicly resolvable.

We then `POST` you a **byte-for-byte copy of Meta's update**, carrying our signature:

```
X-BotYalla-Signature-256: sha256=<HMAC-SHA256(raw_body, your_signing_secret)>
```

Verify it before trusting anything in the payload:

```python
import hmac, hashlib

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(header or "", expected)
```

```js
const crypto = require("crypto");

const verify = (rawBody, header, secret) => {
  const expected = "sha256=" +
    crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(header || ""), b = Buffer.from(expected);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
};
```

**Compute the HMAC over the raw request body**, before any JSON parsing. Re-serialising the
payload reorders keys and breaks the signature.

Respond `200` quickly — our timeout is 10 seconds.

> **No retries today.** If your endpoint is down or slow we log the failure and move on. The
> message itself is never lost — it stays in the BotYalla inbox — but **your copy is not
> re-sent**. If you need delivery guarantees, tell us before you build on this.

## How we handle your secrets

- **Your Meta access token never leaves our server.** You hold a BotYalla key instead, so a
  leak is contained: we revoke that one key without touching your connection or any other
  customer.
- **Secrets are never sent with the page.** They are fetched by a separate request, only
  after you re-enter your own password, and the window closes after 15 minutes.
- **API keys are not stored.** The database holds an HMAC fingerprint only.
- **Webhook URLs must be public HTTPS.** We deliberately reject internal hosts, private
  address ranges and `localhost`.
- **Never send a key or a token over chat or email.** Everything appears in your dashboard
  and nowhere else.

## Limits worth knowing up front

- **The 24-hour window.** More than 24 hours after a customer's last message, you can only
  reach them with a **Meta-approved template**. This is Meta's rule, not ours, and it applies
  to every provider.
- **600 requests per minute** per key. Need more? Talk to us.
- **20 API keys** and **50 team members** per account.
- **Message pricing** is billed to your payment method in Meta — see
  [Meta's official pricing](https://developers.facebook.com/docs/whatsapp/pricing).

## FAQ

**Can I just use BotYalla's number instead of my own?**
No. Your messages would go out from our number, so any spam report would damage its quality
rating and affect every customer on it — and sharing credentials that way breaks Meta's
terms. Your own number is safer for both of us, and it is the number your customers should
see anyway.

**Can I have the raw `WHATSAPP_ACCESS_TOKEN`?**
If you only ever **send**, yes — the developer page can reveal it. But then protecting it is
entirely on you, we cannot revoke it in isolation, and you still will not receive anything.
The key plus the webhook is the better answer in every case.

**What happens when I rotate the webhook signing secret?**
Signatures made with the old secret stop verifying immediately. Update your server first,
then rotate.

**Will the BotYalla bot and my own API fight over the same number?**
No. We process the message **and** send you a copy at the same time. If you want full
control, switch the bot off in your dashboard and keep the webhook running.
